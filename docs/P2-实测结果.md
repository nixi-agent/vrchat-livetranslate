## 3. 渲染质量：两个必须处理的排版问题（视觉复核发现）

| 问题 | 现象 | 修复 |
|---|---|---|
| 英文被从单词中间劈开 | `transla/ted`、`y/our` | 换成混合切分：**拉丁词整词成 token，CJK 逐字，标点单独**；放不下时整词换行 |
| 中文标点跑到行首 | `。` 被挤到第二行行首 | 加**禁则处理**：行首禁则标点采用悬挂（留在上一行行尾） |

回归测试：`tests/test_wrap.py`（4 个用例：拉丁整词保护 / 避头尾 / 行首空格 / 渲染不崩）。
> 注：CJK 内部仍可能在词间断行（如「这个」被拆开）——中文需要分词器才能完全避免，字幕场景可接受。

## 4. ⚠️ 本轮抓到的严重 bug：服务端不发 `done` 事件

**现象**：P1 的 chatbox 路径在「theirs」方向跑出 **12 条增量 / 0 条最终版** —— 最后一条增量已是完整句，
但 `is_final` 永不触发，「句末刷最终版」这条需求实际失效。

**定位**（靠新增的 `--log-events` 事件级埋点）：事件流里**根本没有 `response.text.done`，也没有 `response.done`**，
序列在最后一条 `response.text.delta`（6.6s）后直接断掉：

```
t=+ 857ms  input_audio_buffer.speech_started
t=+1208ms  response.created
t=+1217ms  response.text.delta …
t=+6629ms  response.text.delta     ← 之后服务端一直沉默，没有 speech_stopped、没有 done
```

**原因**：服务端**靠检测静音来收尾一段话**。持续喂音频、尾部又没留静音时，response 会一直挂着。

**修复**：`QwenLiveTranslateSession.tick()` 静默兜底（由 app 的 pump 每 0.3s 调用）——
静默超过 `final_silence_s` 就把累计文本作为最终版发出。**两个细节都是踩出来的**：

1. **阈值必须大于服务端的增量间隔**：实测连续说话时相邻 delta 可间隔 **2.3s**，
   第一版阈值 1.2s 导致在 2.59s 抢跑，把半句「你好。」当成最终版 → 默认改为 **3.0s**。
2. **不能一次终结就永久封死**：长句后续还有增量，
   改为「文本与上次最终版不同才终结」（`_last_final_text` 比对），允许再次终结。

修复后重跑：4 帧、最后一帧完整 ✅

## 5. 刷新策略：两条输出路径的节流是**独立**的（重要）

**需求**：chatbox 受漏桶限制（5 条/5 秒）必须节流；**手腕屏是本地显示，不受任何限制——有更新就该立刻上屏**。

早前把两个输出接到同一个节流器上是设计错误（2026-09-24 修正）：

| 输出 | 策略 | 实测帧数（同一段 8.56s 音频） |
|---|---|---|
| chatbox | 2 秒节流 + 终版必刷（首 delta 立即发） | 6–7 条 |
| overlay | **有增量立刻刷**（`overlay.interval_s: 0`），终版无条件立即刷 | **12–18 帧** |

配置：`overlay.interval_s`（0 = 每次增量都刷；怕晃眼才调 >0）、`merger.interval_s`（chatbox 节奏）。

## 6. 终版去重（修掉的第二个 bug）

三条路径都可能对同一段文本触发终结：`静默兜底 tick()` / `response.done` / `response.text.done`。
实测出现同一句最终版被下发两次（chatbox 因此白发一条）。修法：**去重集中到 `_emit()`**——
`is_final` 时若文本与上次终版相同则直接返回，三条路径共享同一道闸。

## 7. 静默阈值是**用数据定的**，不是拍的

统计 6 次运行的 96 个「增量→增量」间隔：

| 指标 | 值 |
|---|---|
| 中位数 | **0.01s**（增量成簇到达） |
| P90 | 1.04s |
| **最大** | **2.15s** |

→ 静默兜底阈值必须 > 最大间隔，取 **3.0s**（余量 0.85s）。
另外验证了一件事：日志里出现过的「句子中途终版」（`…we're going to test out`）**不是兜底误触发**，
而是**服务端自己的 `response.text.done`**（它在 6388ms 主动切段，6732ms 又开新段）——
说明服务端会自行分段，我们的兜底只在它彻底沉默时生效。
