## 4. 过程中发现并修掉的真 bug

**「最终版必达」被限流桶吃掉。** 第一轮跑出：
```
[chatbox] → 增量 Hello / ...we / ...test out the
[chatbox] ⚠️ 限流丢弃（bucket dropped=1）
[chatbox] ⚠️ 限流丢弃（bucket dropped=2）    ← 最终版没了，用户永远看不到完整句
```
根因：漏桶（5 条/5 秒 + 最小间隔 0.4s）对「增量」和「最终版」一视同仁，而**最终版是不可弃的**。
修复：`Chatbox` 增加 `_pending` 队列——最终版被拒时入队而非丢弃，由 `app` 的补发泵（每 0.3s）等窗口到了补发；
收尾时还会多等最多 6 秒把队列排空。第二轮验证：`最终版待补发 0 条`、#8 报文确实送达。

## 5. 待观察 / 已知行为

1. **服务端会把一段话切成多个响应段**（本次 8.56s 语句被切成 2 段）：第一段是主句，第二段是后半句。
   默认 `merger.carry_over: false` → 气泡只显示最新段。要「连续字幕」观感可置 `true`（会把上一段最终版作为前缀，注意 144 字符上限）。
2. 第二段的最终版在本次 settle 窗口内没到达（应用已退出）；正式运行是常驻进程，不存在这个问题。
3. **UDP 端口复用的坑**：同一个端口起两个监听器（都开了 SO_REUSEADDR）时，内核只把包投给其中一个，
   会误判为"没收到"。调试时确保只有一个监听器。

```bash
.venv/Scripts/python.exe scripts/osc_listen.py
```
