# 验收与门禁

> 仓库的验收分成**四层**，各层回答不同的问题。别把某一层的绿当成另一层的证据 ——
> 「单测全绿」证明不了「接在界面上那条路真的跑了」，「CI 绿」也证明不了「真机上用户看得见」。
>
> 各脚本自己的用法不再复述：跑测试看 [CONTRIBUTING.md](../../CONTRIBUTING.md) §二，
> 真机脚本看 [scripts/verify/README.md](../../scripts/verify/README.md)，发版清单看 §七。

---

## 一、四层各回答什么

| 层 | 回答的问题 | 载体 | 跑在哪 |
|---|---|---|---|
| ① 离线单测 | 纯逻辑对不对（不碰真设备 / 不联网） | `tests/`（脚本式，**不是 pytest**）| 本机 + CI 两腿 |
| ② CI 门禁 | 提交进得来吗（语法 / 静态 / 凭据 / 打包 / 平台隔离） | [.github/workflows/ci.yml](../../.github/workflows/ci.yml) | GitHub runner |
| ③ 真机验收 | 功能在**真实环境**里跑通了吗 | `scripts/verify/` | 维护者本机（**不进 CI**） |
| ④ 发布复核 | 交付给用户的那个产物是不是对的 | `.github/workflows/release.yml` + [scripts/verify_release.py](../../scripts/verify_release.py) | tag 触发 + 本机复核 |

## 二、本地（提交前）

```bat
:: 全量：仓库唯一的运行器，与 CI 同口径（逐文件跑，自动跳过需要真 key 的 test_engine.py）
.venv\Scripts\python.exe scripts\run_tests.py

:: 只跑名字含关键词的
.venv\Scripts\python.exe scripts\run_tests.py --only i18n

:: 附覆盖率摘要（不设阈值、不阻断）
.venv\Scripts\python.exe scripts\run_tests.py --coverage

:: 静态门禁（CI 里是阻断项）
.venv\Scripts\python.exe -m ruff check --select F,E9 .

:: 文档相对链接 / 锚点（**只加在 CI 的 Linux 腿**，本地先跑一次省一轮往返）
.venv\Scripts\python.exe scripts\check_doc_links.py
```

其它可用开关（细节见脚本头部 docstring）：`--with-engine`（连 `test_engine.py` 一起跑，需真 API key）、
`--require-tk` / `--require-xvfb`（缺了就**判红**而不是静默少跑一批）、`--xvfb-screen`、
`--no-xvfb`、`--no-gha`。

⚠️ 解释器**一律用仓库 venv**：本机与 CI 都**没有 `python3`**；裸 `python` 缺 `pythonosc` 等依赖，
会 35 个用例秒红（看着像代码坏了）。

## 三、CI 的门（四条腿）

触发：push 到 `main`、开/更新 PR、手动 `workflow_dispatch`。**推分支不会触发** ——
分支自己跑一遍要手动 `gh workflow run ci.yml --ref <分支>`。

| 腿（job） | runner | 跑什么 |
|---|---|---|
| `tests` | windows-latest | 装依赖 → 断言 Windows 独占依赖可导入（`openvr` / `pyaudiowpatch`）→ `compileall` → **ruff F,E9（阻断）** → `check_no_secrets.py --once` → `run_tests.py --coverage --require-tk --require-xvfb` |
| `package` | windows-latest | `build_exe.py --no-verify` → 断言产物可用 → **`check_platform_purity.py --platform windows`**（产物里不许有 Linux 独占实现） |
| `linux-tests` | ubuntu-latest | 装系统依赖 → `compileall` → ruff → `check_no_secrets` → **`check_doc_links.py`** → `run_tests.py --coverage --require-tk --require-xvfb` |
| `appimage` | 复用 [.github/workflows/appimage.yml](../../.github/workflows/appimage.yml) | Linux 打包链路（含模块对账：磁盘上每个 `vlt/**.py` 都要在包里） |

两条注意：

- **文档链接检查只在 Linux 腿**：Windows 腿绿 ≠ 文档链接没问题。
- PR 与 `main` 有冲突时，`pull_request` 触发的 CI **一次都不会跑**（GitHub 建不出 merge ref），
  `gh pr checks` 会显示 `no checks reported`。别读成「CI 绿」——先把 `main` 合进分支解冲突再推。

## 四、真机验收（③）

`scripts/verify/` 是**入库的**真机脚本（以前只在维护者本机的 `out/`，别人复现不了）。
它们不进 CI（需要真桌面会话 / Win32 能力 / 真虚拟声卡 / 联网），用途是**让验收可复现、让评审看得见**。

- 每份要什么硬件、会不会写盘、实测状态：[scripts/verify/README.md](../../scripts/verify/README.md)
- 约定：去硬编码路径、**只写 `out/` 或临时沙箱**、缺硬件时几秒内明确报错（禁 hang / 禁静默跳过）
- 临时的一次性探针脚本不要留在仓库里；能复用的验收脚本往 `scripts/verify/` 放

## 五、发布与复核（④）

- [.github/workflows/release.yml](../../.github/workflows/release.yml)：推 `v*` tag 触发 →
  **对账 tag 与 `vlt/__init__.py` 的 `__version__`**（不一致直接失败）→ 打 exe → 取回 AppImage 产物 →
  自检产物 → **覆盖式发布到 Cloudflare R2 并走公开域名复核（`publish-r2`）** → 建 Release，
  附件为 exe + AppImage + `SHA256SUMS.txt`。

  ⚠️ `publish-r2` 是 `release` 的**前置**（`needs`）：客户端 v0.12.0 起主要从 R2 收更新，
  「发了版但用户收不到」必须整体红。R2 那一步干三件事：算 sha256 → 生成 `latest.json`
  （客户端契约，格式见 [scripts/publish_r2.py](../../scripts/publish_r2.py) 头部）→ 上传四个**固定键**
  （全部带 `Cache-Control: no-cache`，理由同该脚本头部）→ 把两份产物**整份下回来逐字节复核**。

  `SHA256SUMS.txt`（上传前**门禁**，`_check_sums_file`）：若在，必须 exe 与 AppImage **各一行**、
  值与真实产物逐项一致，且**不许有 CR**（CRLF 会让 Linux 侧 `sha256sum -c` 整份核不过 ——
  这个文件的读者正是 Linux 用户）。生成侧因此走 `[System.IO.File]::WriteAllText` 显式写 LF，
  不用 `Out-File`（Windows runner 上它是 CRLF）。
- 复核产物：[scripts/verify_release.py](../../scripts/verify_release.py) —— SHA256 对账、**真跑
  `--self-test`**、版本行、字节码里搜新功能字符串（needle）、图标像素比对；
  并**顺带对账主更新源**（清单版本 == tag、清单 sha256 == GitHub digest、公开域对象字节数 == 附件 size、
  公开域那份 `SHA256SUMS.txt` 里两个平台各占一行且与清单一致）。
  那份 `SHA256SUMS.txt` 不按字节跟 GitHub 比：R2 侧自 2026-10 起是两行，而已发布的旧 Release
  附件里仍是一行（旧附件不改）——判据改成「R2 那份**不少于** GitHub 那份」，内容由上面两条逐行钉住。
  needle 参数里放**本次改动独有的字符串**，否则复核证明不了「新代码在包里」。
- 客户端视角的更新链路体检（真实入口、真下载、真校验）：
  [scripts/verify/verify_update_source.py](../../scripts/verify/verify_update_source.py)
  —— 它回答的是「用户到底收不收得到更新」，与上面「我发出去的东西对不对」是两个问题。
- 交付给用户的 exe **文件名必须纯 ASCII**（中文名会让 OpenVR 初始化直接失败）。诊断包与正式包
  版本号可能相同，靠**包名**区分构建标记。

## 六、改动面 → 至少跑到哪一层

| 改动面 | 最低验证 |
|---|---|
| 纯文档 / 注释 | `check_doc_links.py`（+ 涉及 `.py` 时 `ruff`） |
| 词表 / 新增界面语言 | `tests/test_i18n.py`、`tests/test_langs.py` + **真窗口布局体检**（逐控件比 `reqwidth` / 实际宽，五种语言都来）；界面语言跟随系统 → 构造 GUI 的用例要**先钉死语言** |
| 模块拆分 / 函数签名变更 | `tests/test_wiring_signatures.py` + 全量；搬家的公共全局（如字体常量）要确认重绑 |
| 新增/删除平台独占模块 | 构建脚本里**两份**禁列清单 + `check_platform_purity.py` + 模块对账 + [docs/平台约束记录.md](../平台约束记录.md) §三 的清单 |
| 采集 / 重采样 / 门限 | `tests/test_resample.py`（判据是相关性/主频，不是「跑通」）+ 真机回环脚本 |
| 手腕屏 / 桌面字幕 | 假对象单测 + `scripts/verify/` 对应脚本 + **改自愈阶梯时先跑旧路台阶那条用例** |
| 界面控件 / 布局 | 真窗口布局体检；设置窗按宽守卫（未映射也要可靠，别用「真显示设置窗」当 CI 守卫） |
| 更新链路 | `tests/test_update_check.py`、`tests/test_update_dialog.py`（注意历史残留，见 [踩坑索引.md](踩坑索引.md)） |
| 打包 / 发布 | `build_exe.py` + 产物自检三件套 + `verify_release.py` |

## 七、反「假绿」纪律（都是踩出来的）

1. **离线是硬要求**：新用例必须离线可跑。验证方法：用死代理（`HTTP_PROXY=http://127.0.0.1:1`）
   跑一遍仍全绿。
2. **故障注入**：新增的守卫用例，**把修复点改回旧写法必须变红**。写完就注入一次；
   「代理说全过」不算证据，主控/维护者自己注入。
3. **断言要钉住该级独有的行为**：自愈类用例只断言「碰巧出现了新对象」会假绿（硬重启里顺带也会重建）。
4. **状态类断言要卡在触发那一帧之后立即断**，多跑一帧会被「随后成功」把状态重置掉。
5. **全量测试一次只跑一份**：各用例共用沙箱与仓库根的 `config.yaml`，并发跑或被 kill 会互相踩出假红。
6. **尺寸 / 几何类断言要钉死虚拟屏**（CI 用 `VLT_XVFB_SCREEN` 覆盖）：
   `xvfb-run -a -s '-screen 0 1920x1080x24'`。裸跑宿主屏的数字不可当判据。
7. **产物自检的判据是三件套**：退出码 0 + stdout 有 `GUI_SELFTEST_OK` + **本次**那份日志里也有
   （构建脚本末尾的判定可能读到上一份日志而误报）。
8. **`tail` 后面别取 `$?`**：管道里拿到的是 `tail` 的退出码，永远是 0，不能当 CI 结论。
   要结论用 `gh run view <id> --json jobs --jq '.jobs[] | "\(.name): \(.status)/\(.conclusion)"'`。
